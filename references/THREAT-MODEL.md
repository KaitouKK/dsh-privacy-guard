# 威胁模型与防护设计说明

本文件说明 dsh-privacy-guard 针对「个人智能体 / 个性化智能体」场景的威胁模型、防护分层与设计取舍，是插件实现的依据。对应调研来源见主报告。

## 1. 威胁模型

个人智能体（如 DSH、OpenClaw 类）具备文件读写、命令执行、网络访问、上下文记忆能力，因此攻击面远超普通聊天模型。核心威胁分四类：

| 编号 | 威胁 | 描述 | 典型路径 | 危害 |
|---|---|---|---|---|
| T1 | 提示词注入（直接/间接） | 外部数据（网页、文档、消息）携带隐藏指令，诱导 Agent 把「数据」当「指令」 | Web 抓取结果回灌、文档内容嵌入指令、多轮对话劫持 | 越权操作、系统被控（相当于拿到远程主机） |
| T2 | 敏感信息窃取 / 外带 | 诱导 Agent 输出 API Key、Token、凭据、记忆、聊天记录，或主动外发数据 | `Print your API keys`、`upload all files to <url>` | 密钥泄露、数据出域 |
| T3 | 误操作 / 权限滥用 | Agent 自主执行高风险动作（递归删除、覆盖源码、格式化、关机）无人工把关 | 自动化任务链中的误判、被注入后执行 | 数据丢失、系统损坏 |
| T4 | 日志与结果泄露 | 处理过的 PII 原样进入上下文/日志/输出，被后续环节或第三方获取 | 日志记录原始手机号/身份证、结果文件含密钥 | 隐私违规（个保法）、二次泄露 |

## 2. 防护分层（纵深防御）

```
        [输入层]               [执行层]              [输出层]
外部数据 ──▶ 注入检测(T1) ──▶ 审批拦截(T3) ──▶ 结果回扫脱敏(T4)
   │            │                  │                 │
   │       PII 提前脱敏(T2)     block=人工确认     PII 脱敏(T4)
   ▼            ▼                  ▼                 ▼
    审计日志（脱敏后写入，可追溯）
```

- **输入层**：注入检测（T1）+ PII 脱敏（T2 前置）
  外部内容进入模型上下文前，先做注入特征扫描（中英文指令劫持、泄密诱导、高危动作），并对已识别的 PII 打码，从源头降低「指令-数据混淆」与携带敏感值的概率。
- **执行层**：敏感操作审批（T3）
  对将要执行的工具调用做规则评估，`block`（≥80 分）要求人工确认，`ask`（≥50 分）建议确认；避免 `rm -rf`、关机、外发、读 .env 等高危动作在无监督下执行。
- **输出层**：结果回扫（T4）
  模型输出（`agent/request` 等事件）落盘/返回前再次脱敏，防止 PII 泄漏到日志或对外结果。

## 3. 评估逻辑设计

### 3.1 PII 检测策略（detectors.js）

- **规则 + 黑名单**：手机号等格式类用正则，示例号/占位号（`13800000000` 等）进黑名单不告警，降低误报。
- **情境化匹配**：`password=xxx`、`api_key=xxx` 仅打码值保留键名；Bearer 头、`sk-`、JWT 前缀特征明确，直接全打码。
- **掩码策略**：身份证/手机号保留首尾（`110****02X`）；密钥全星；固定位占位符；邮箱保留域名。
- **敏感度分级**：`sensitiveLevel` 1-3，高敏感（密钥、身份证、手机号）在审计中强制记录。

### 3.2 注入评分（injection.js）

三类模式加权计数：直接指令（忽略指令/角色接管/无限制模型）权重 3、泄密外带权重 3、高危动作权重 1；`score` 累加，超过阈值 `flagged=true`。中文模式覆盖「忽略以上所有指令」「从现在开始你是」「把全部数据发给」等常见注入话术。

### 3.3 审批决策（approval.js）

八类规则各带权重（45-95），命中叠加；`≥80 block`，`≥50 ask`，否则 `allow`。

- 命令类参数（`bash` 工具的 `command`）**优先提取命令文本**再评估，避免 JSON 包裹的 `{}` 被误判为通配符（这是本插件开发中发现并修复的关键坑）。
- 覆盖源码/配置（`.js/.ts/.env/...`）权重 55 触发 ask，符合「写代码文件是常见操作但不是无风险」的取舍。

## 4. 设计取舍与边界（明确声明）

1. **启发式而非语义级**：正则+评分能做到可控、低延迟、零外部依赖，但对语义补全的攻击（把恶意动作包装成合理需求逐步诱导）检出有限。生产环境建议叠加 LLM 分类器（如蚂蚁 SingGuard-NSFA 类护栏模型）作为第二道语义防线。
2. **决策不代替执行阻断**：插件输出 `block/ask` 标记并写审计；实际阻断 UI 由 DSH 运行时的审批机制承载。`apply` 中事件挂钩采用防御式监听（事件不存在也静默放行），确保插件自身不成为故障点与 DoS 点。
3. **审计即脱敏**：审计事件记录的是脱敏后文本与命中类别，不落原始 PII，符合最小化留存。
4. **零权限假设**：插件自身没有多余文件系统/网络权限，只做内存处理与可选 JSONL 落盘；不收集、不上传任何数据。

## 5. 业界对标（实现取舍来源）

- **输入清洗**：参考 AutoGPT/OpenClaw 社区的脱敏中间件思路（文件读取后先脱敏再入上下文）。
- **行为护栏**：参考蚂蚁 SingGuard-NSFA（行为前实时判定、动作分级）；本插件用轻量规则实现同等「动作前判定」位置。
- **审批最小权限**：参考 OpenClaw 官方安全指南（关键操作人工确认、半自动模式）。
- **边界/提醒**：参考「不向智能体提供密码/密钥」守则——插件检到密钥直接打码并告警，不鼓励在上下文中传递凭据。
